## 2. Evaluator defects found and repaired before baselining

These are evaluator repairs, not prompt revisions, and are not counted as iterations.

1. **The grader never saw the inputs (critical).** The five `llm-rubric` assertions in `evals/storyboard.yaml` instruct the grader to assess the storyboard "against the provided StoryBrief, World, and CharacterSet", but the rubric text contains none of the three, so the grader could not check character, world or causal consistency against them. The new rubrics inline `{{STORY_BRIEF_JSON}}`, `{{WORLD_JSON}}` and `{{CHARACTER_SET_JSON}}`.
2. **Rubrics were not itemised and scored fractions.** The old rubrics gave a 1-5 anchor description only at the endpoints and asked for `score = integer/5.0` against a 0.8 threshold, which invites inconsistent judging and makes grader failures (score 0) hard to separate from low scores. The new rubrics list five checks (a)-(e) per criterion, define every score level, use integer 1-5, pass at >= 4, and ask for evidence by scene id. Criteria and weights are unchanged (causal coherence 30, character consistency 25, narrative structure 20, world consistency 15, pacing 10); the five criterion names are unchanged. The old "a high pacing score must not compensate" line is dropped because each criterion is now judged independently and the pass rule is "every assertion passes".
3. **Deterministic results were a single bit.** `storyboard_assert.py` returns one pass/fail, so schema validity, referential integrity, dependency validity and phase correctness could not be reported separately. `evals/storyboard_stage3_assert.py` adds one assertion per facet by classifying the existing validator's `ErrorCode`s (no rule added or relaxed), plus `format_discipline` (the prompt demands JSON only; the provider's JSON extraction would otherwise hide fences and prose). `storyboard_assert.py` stays in the frozen set as `structural_validity`. When the schema fails, the validator stops before semantic checks; those three facets are reported as `NOT_EVALUABLE` rather than counted as passes or genuine violations, and the case still fails through `schema_validity`.
4. **No dev/holdout tag in the test file.** `evals/storyboard_stage3_tests.json` is generated by `scripts/generate_storyboard_stage3_tests.py` from the existing `storyboard_tests.json` (same 35 cases, same fixtures; only `metadata.split/case` added from the brief path) so the split can be selected with `--filter-metadata`.

`evals/storyboard.yaml` and `evals/storyboard_tests*.json` are left byte-identical (the original smoke configuration stays listed in the manifest).

No calibration pilot was run before freezing; rubric difficulty is untested and may be at or near ceiling (see limitations in the iteration log).

## 4. Case-level rule

A case passes only if every applicable assertion passes: `structural_validity`, the four validity facets, `format_discipline`, and all five rubrics at integer score >= 4. Provider errors (generation never produced output) and grader errors (grader call failed or returned no usable JSON) are infrastructure failures: they are listed, excluded from the "scored" denominator, and also reported in a strict rate over all attempted cases.

## 5. Run protocol (model calls are made by the user)

.venv/bin/python scripts/storyboard_stage3.py run v1 dev --jobs 3      # -> results/v1_dev.json (+ .summary.json)
